# Budget & Expenses

Implemented from the approved Stitch Budget & Expenses screens in project `9719362010133116550`. Private pages: `/budget`, `/budget/edit`, `/budget/expenses/new`, `/budget/expenses/[expenseId]`, and `/budget/expenses/[expenseId]/edit`. The dashboard budget card uses the same real summary. No sample records are seeded.

APIs: `GET/PUT /api/v1/budget`, `GET/POST /api/v1/expenses`, `GET/PUT/DELETE /api/v1/expenses/[expenseId]`, and `GET /api/v1/expenses/summary`. The summary returns wedding-wide budget, expenses, paid, outstanding, remaining, utilization and category/event/payment-status groups. `GET /api/v1/dashboard?section=budget` returns that summary; the full dashboard response adds an independent budget section. Responses are allowlisted and never include raw database documents.

The approved form stores seven documented fields: name (120 characters), category (80; default suggestions or custom text), amount, paidAmount (default 0), optional eventId, optional paidByName (120), and optional notes (5000). Payment status is derived and persisted: zero paid = UNPAID, paid equals amount = PAID, otherwise PARTIALLY_PAID. Outstanding = amount minus paid. Amount must be positive, budget/paid nonnegative, paid cannot exceed amount; finite amounts support two decimal places within safe integer cents. Optional fields can be explicitly cleared; partial updates preserve omitted values. Existing paidByUserId is preserved but no member-payer selector is introduced.

Budget is the existing wedding totalBudget field; unset is null in the response, distinct from a saved zero. Remaining = budget minus total expenses. Utilization is unavailable for unset/zero budgets and may exceed 100%; the visible progress track clamps at 100% while retaining the actual percentage. Negative remaining is displayed as a positive “Over budget by” amount. Global metrics and breakdowns do not change when filtering the paginated newest-first expense list. Filters combine literal name search, category, event (including Wedding-wide), and payment status; lists default to 20, maximum 100.

Scope and authorship derive from the server session. Central permissions allow all members to read, OWNER/ADMIN to manage. Mutations require same origin, bound JSON to 32 KiB, and share a durable 60-per-minute user limit for budget/expense changes using the approved rate_limits collection. Only the existing documented expense weddingId index is provisioned lazily. No schema fields, collections, indexes or dependencies were added.

Event links are checked within the same wedding in a transaction. A write to the existing event updatedAt serializes linking with transactional event deletion; deleting an event keeps expenses and clears their links. Expense deletion is a confirmed hard delete of only that expense; subsequent summaries recalculate paid and total amounts. Details show created/updated timestamps in IST. Failure states retain form data and permit retry; independent summary/list loading does not replace failures with fake zero values.

The Activities increment (2026-10-08) records an automatic expense-added update atomically with creation, including its recorded INR amount and optional event link. Expense/payment edits and deletion do not generate another update. See ../activities/README.md.

Receipts/documents, structured vendors, payment dates/installments, payment processing, category budget allocations, family sides, individual member selection and cross-browser live synchronization remain outside the implemented scope. Unresolved specification conflicts remain in FOUNDATION_DECISIONS.md; this implementation does not decide or enable those fields/features.
